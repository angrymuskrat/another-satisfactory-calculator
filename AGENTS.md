# Инструкции для агентов

## Назначение

Персональный русскоязычный калькулятор Satisfactory: оптимизация производства,
ограничения ресурсов и технологий, пользовательские профили, современный UI без Sankey.
Это основной файл инструкций. `AGENT.md` только ссылается на него.
Общение и проектная документация — на русском; идентификаторы кода — на английском.

## Перед работой

1. Прочитать этот файл, `docs/STATUS.md` и спецификацию текущей задачи.
2. Проверить Git и существующие изменения. Не перезаписывать чужую работу.
3. Отличать требования пользователя, согласованные решения и предложения.
   Черновик архитектуры не является утверждённой реализацией.
4. Брать ограниченную задачу с проверяемым результатом. При параллельной работе
   заранее назначать владельцев файлов и согласовывать общие контракты.

## Требования, которые необходимо сохранить

- Два режима: максимум выпуска из доступных ресурсов; заданный выпуск с минимумом энергии.
- В обоих режимах можно ограничивать ресурсы явными потоками или месторождениями.
- Для нескольких продуктов реализовать ВСЕ три политики с переключением:
  заданные пропорции, последовательные приоритеты, взвешенный выпуск.
- Учитывать выпуск, энергопотребление и расход сырья; порядок целей должен быть явным.
- Выбор доступных зданий, добывающих установок и пропускной способности транспорта.
- Включение и выключение альтернативных рецептов, поиск и категории как в игре.
- Русификация интерфейса, названий и поиска; стабильные ID не зависят от языка.
- Сохранение рецептов, зданий, мощностей и ограничений в профиле конкретного пользователя.
- Отдельный frontend и небольшой backend для пользовательских данных.
- Результаты в таблицах, карточках и раскрываемых этапах; Sankey не добавлять.

## Вычислительные правила

- Ядро расчёта не зависит от UI и хранилища пользователей.
- Балансировать каждый предмет, жидкости, побочные продукты и циклы совместно.
  Не подменять оптимизатор рекурсивным деревом или жадным выбором рецептов.
- Недоступные рецепты и здания исключаются до решения модели.
- Различать «ресурс запрещён», «ограничен» и «не ограничен»; ноль не означает бесконечность.
- Не складывать сырые значения MW, предметов/мин и м³/мин в одну необъяснённую цель.
- Указывать границы энергетического расчёта: добыча, производство, утилизация,
  внешние поставки; не считать неизвестную энергию поставок доказанным нулём.
- Различать среднюю и пиковую мощность, дробную загрузку и физическое число зданий.
- Учитывать ограничение выхода каждого добытчика. Одна лента не ограничивает
  всю фабрику при разрешённых параллельных лентах.
- Для оптимизации частот нужны явные пределы и модель количества машин.
  Изменение частот после расчёта может изменить энергетический оптимум.
- Не скрывать избытки и отходы. У каждого потока должно быть назначение;
  складирование не является бесконечной утилизацией стационарной фабрики.
- Не называть результат оптимальным без соответствующего статуса решателя.
  Показывать невыполнимость, неограниченность, тайм-аут и допустимое приближение отдельно.

## Данные игры и заимствования

- Исходный ориентир: https://github.com/KirkMcDonald/satisfactory-calculator .
- При импорте фиксировать commit/hash, версию игры, источник, дату и статус проверки.
- Не считать upstream JSON автоматически актуальным. Сверять рецепты, здания,
  транспорт, добычу, мощность и локализацию с данными соответствующей сборки игры.
- Хранить исходные данные, нормализованные данные и ручные исправления раздельно.
  Не править генерируемый каталог вручную.
- Сохранять авторство и лицензионные уведомления заимствованного кода;
  учитывать происхождение игровых изображений отдельно от лицензии кода.
- Не выдавать приблизительные переводы или группы за точное соответствие меню игры.

## Проверки и готовность

- Для ядра проверять вручную вычисляемые примеры, материальный баланс,
  ресурсные лимиты, смену рецепта при ограничениях, циклы и все три политики выпуска.
- Для API проверять сохранение, повторную загрузку, валидацию и изоляцию пользователей.
- Для UI проверять оба сценария расчёта, поиск на русском, переключение рецептов,
  профили, ошибки и доступность клавиатурой.
- Команды запуска, сборки и тестов добавлять в README после их фактического появления.
  Действующие команды: `pnpm dev`, `pnpm test`, `pnpm typecheck`, `pnpm build`,
  `pnpm test:ui`; без package manager уже установленный проект запускается
  через `node scripts/dev.mjs`. Node.js 24+. Подробнее в README.md.
- Перед отчётом о готовности запустить относящиеся к изменению проверки.
  Прямо сообщать, что не запускалось или не проверено.

## Реализованная структура и дополнительные инварианты

- `apps/web`: React/Vite, worker и profiles UI; `apps/api`: Fastify/SQLite.
- `packages/domain`: контракты и runtime validation; `packages/solver`: модель,
  последовательные цели и независимый валидатор; `packages/game-data`: импорт.
- Частоты V1 заданы пользователем; выходные потоки и MW соответствуют средней модели.
- HiGHS adapter генерируется `scripts/prepare-highs.mjs`: нельзя возвращаться к
  pretty-выводу зависимости (он округляет колонки и ломает последовательные цели).
- Пропорции и веса нормализуются, произвольный общий множитель не меняет выпуск.
- Утилизаторы целочисленные, требуют отдельного `mip_feasibility_tolerance`.
- Следовые потоки нельзя удалять из результата без повторного решения модели.
- Независимый validator пересчитывает лимиты и мощность из Plan/Catalog, не доверяет
  значениям limit/power в самом результате.
- `Source.limit` для node — дополнительный cap. При смене flow→node UI сбрасывает
  прежний cap в null; водозабор всегда purity=1.
- Группы рецептов пока ручные; не отмечать их точным игровым соответствием без новых
  источников. Порядок внутри групп импортируется из mManufacturingMenuPriority.
- Не коммитить `.data`, `node_modules`, `.pnpm-store`, generated vendor, dist и output.
