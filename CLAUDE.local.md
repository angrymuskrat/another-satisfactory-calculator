# CLAUDE.local.md — персональные правила работы в этом репозитории

Дополняет `AGENTS.md`: там правила проекта, здесь мои рабочие SOP.
Явные указания в текущей задаче имеют приоритет над этими правилами.
Перенесено из synapse (`CLAUDE.local.md`, разделы 1, 7–9) и адаптировано.

## 1. SOP — как работать со мной

1. **Коммитить только по прямому требованию. Самостоятельно не делать `git commit`,
   в том числе после успешных проверок.** Завершённая задача не является разрешением
   на коммит. Push и деплой — тоже только по запросу: push в `master` запускает
   `.github/workflows/deploy.yml`, который после проверок обновляет стенд.
2. Не печатать содержимое `.env*`, ключи, пароли и Authorization headers
   в логи, отчёты, коммиты и описания PR.
3. По окончании сообщать об изменённых файлах и выполненных проверках, оставляя
   изменения незакоммиченными, если коммит не запрошен.
4. **Скиллы — только по согласованию.** Перед работой классифицировать задачу по
   разделу 2 и предложить набор по SOP раздела 3; вызывать скиллы после моего
   согласия. Это правило выше автозапуска из `using-superpowers`, `nav-brief`
   и `nav-workflow`. Исключение — чеклист раздела 4: он не скилл и выполняется
   без согласования.

## 2. Классификатор задач → скиллы

Проектные скиллы лежат в `.claude/skills/`: `simplest-fix-first`, `deep-investigation`,
`pre-ship`, `review-advanced`, `sloppy-job-review`, `grilling`. При пересечении
с superpowers или navigator берётся проектный. Цепочка читается слева направо;
«опц.» — предлагать, только если сигнал явно есть.

## 3. SOP: классификация и согласование скиллов

1. **Классифицировать** запрос по сигналам раздела 2. До согласования разрешена только
   разведка, нужная для классификации и не меняющая состояние: `git status`, чтение
   PR, файла, памяти.
2. **Класс 0** — работать сразу, ничего не предлагать.
3. **Класс неоднозначен** (подходят два класса или сигналы спорят, например «баг»,
   а по сути новое поведение) — задать один вопрос через `AskUserQuestion`
   с вариантами-классами, рекомендуемый первым. Работу не начинать.
4. **Предложить набор** одним блоком:
   `Класс: A (инцидент). Предлагаю: deep-investigation → simplest-fix-first → TDD → pre-ship. Пропускаю: systematic-debugging (дублирует). Ок?`
   Указывать, почему выбран класс, если это не очевидно из запроса.
5. **Ждать согласия.** Принимается правка набора («без TDD», «добавь grilling»).
   Явный вызов `/<skill>` пользователем — уже согласие на этот скилл.
6. **После согласия** вызывать скиллы по порядку и коротко объявлять каждый.
   Скиллы, не вошедшие в согласованный набор, не запускать, даже если их описание
   требует автозапуска.
7. **Класс сменился по ходу** (например, фикс упёрся в новую функциональность) —
   остановиться, назвать новый класс и предложить добавку к набору; снова ждать согласия.
8. **Согласие действует на текущую задачу** и не переносится на следующие запросы.
   Если сказано «на эту сессию без согласования» — не спрашивать до конца сессии.
9. **Скиллы не дают прав** на commit, push, деплой и комментарии в PR —
   эти действия по-прежнему по разделу 1.
10. **Классификатор ошибся** (пользователь поправил класс или набор) — после задачи
    предложить правку таблицы раздела 2, чтобы сигнал учитывался дальше.

## 4. Чеклист перед PR — обязателен, не требует согласования скиллов

Выполнять перед любым «готово», «можно коммитить», «собери PR» и перед передачей
PR на ревью. Итог — таблица «проверено / не проверено» в ответе; пропущенный пункт
называть явно с причиной, а не опускать молча.

1. **Прогон на смерженном дереве.** Временно смержить свежий `origin/master`;
   запустить `pnpm typecheck`, `pnpm test`, `pnpm build`, `pnpm test:ui`.
   CI на PR запускает только `typecheck` и `test` (`.github/workflows/deploy.yml`),
   поэтому сборка и UI-тесты проверяются только локально.
2. **Соседние ветки.** `gh pr list --state open` и ветки параллельных сессий
   (`git branch -a --list '*claude/*' '*codex/*'`); для каждой, трогающей те же
   файлы, `git merge-tree` с её головой. Бесконфликтный мерж тоже проверять тестами.
3. **Переносы и удаления.** `git diff --name-status --diff-filter=RD origin/master...HEAD`;
   старый путь искать по всему репо, включая AGENTS.md, README, `docs/`, `scripts/`,
   `Dockerfile`, workflows, `tests/ui/` и пути в код-спанах. У перенесённых модулей
   проверить относительные импорты и `new URL(..., import.meta.url)`: rename со 100%
   сходством не попадает в дифф, и относительный путь ломается молча.
4. **Инварианты.** Grep AGENTS.md и `docs/*.md` по модулям и понятиям диффа.
   Если PR меняет записанное там правило, в том же PR обновить AGENTS.md или
   спецификацию; прогресс и следующий шаг — в `docs/STATUS.md`.
5. **Комментарии во всех типах файлов.** Выписать каждую добавленную или изменённую
   строку комментария из диффа: `.ts`, `.tsx`, `.mjs`, `.yml`, `Dockerfile`, `.env.example`,
   блоки кода в `.md`. По каждой — вердикт Delete или Rewrite по проходу 9 `pre-ship`;
   вердикт по умолчанию Delete. Плотность комментариев — как в окружающем коде.
6. **Текст ↔ код.** Каждое утверждение в описании PR, README, AGENTS.md и `docs/`
   подтверждается `file:line`. «Уже было в `master`» проверять по merge-base.
   Новую команду или сценарий из README прогнать с чистого клона буквально по тексту.
7. **Все входы.** Для нового поля или поведения перечислить все пути, которые
   создают те же данные: форма UI, импорт файла настройки рецептов и плана, API,
   гостевой черновик в браузере и workspace аккаунта, мир и фабрика (`effectivePlan`),
   основной расчёт, варианты и анализ в worker. Проверить каждый.
8. **Старые данные.** Для нового поля ответить отдельно: ключа нет, `null`, пустое
   значение, файл другой версии каталога. Сохранённые планы, черновики в браузере,
   workspace в SQLite и экспортированные файлы существуют до фичи; скрытая миграция
   запрещена (AGENTS.md).
9. **Тесты.** Удалённые тесты и изменённые `expect` — отдельный раздел описания PR
   с причиной. Тест, читающий исходник и матчащий regex, — не тест. Для решателя —
   проверки из раздела AGENTS.md «Проверки и готовность».
10. **Описание PR.** Разделы: что меняется (с `file:line`), изменённые или
    удалённые тесты, что проверено, что не проверено. Не описывать того,
    чего в диффе нет, и не приписывать PR поведение, которое уже было в `master`.
