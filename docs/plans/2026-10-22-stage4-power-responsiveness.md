# Этап 4: энергия и отзывчивость

Запрос пользователя 2026-10-21: «реализуй следующую задачу из бэклога» — этап 4
[плана среднего этапа](2026-10-03-mid-game-roadmap.md), оба пункта. Дизайн
согласован в диалоге 2026-10-21/22:

- справка «чем покрыть» — только угольный и топливный генераторы;
- варианты показываются карточками по мере готовности; основной вариант можно
  выбрать до конца расчёта, остальные дорешиваются в фоне.

Отклонённые альтернативы: генераторы в `catalog.json` и типе `Catalog` (каталог
передаётся в worker, валидацию и сохранения, а генераторы в расчёт не входят);
захардкоженные 75/250 МВт и энергоёмкость топлива (данные берутся из сборки);
сразу открывать подробный план основного варианта; отмена остальных вариантов
при выборе основного.

## 4.1 Справка «Чем покрыть»

### Данные

- Новый скрипт `scripts/import-power-generators.mjs` пишет
  `packages/game-data/power-generators.json` из закреплённых
  `source/Docs-en-US.json.gz` и `source/Docs-ru.json.gz`. Хэши сверяются
  с `source/provenance.json`, как в `import-p2-mechanics.mjs`; соответствие
  класс → `itemId` берётся из `audit-report.json` (`itemClasses`).
- Генераторы: `Build_GeneratorCoal_C` (`coal-generator`) и `Build_GeneratorFuel_C`
  (`fuel-generator`), NativeClass `FGBuildableGeneratorFuel`. Поля записи:
  `id`, `className`, `name` (Docs-ru `mDisplayName`), `nameEn`, `power`
  (`mPowerProduction`, МВт), `fuels`, `supplemental`.
- `fuels[]`: `itemId` из `mFuel[].mFuelClass`; `energy` — МДж на единицу
  каталога: для твёрдых — `mEnergyValue` на предмет, для жидкостей и газов —
  `mEnergyValue × 1000` на м³ (единица Docs для жидкостей — 1/1000 м³, как у
  `mItemsPerCycle` в `import-p2-mechanics.mjs`).
- `supplemental`: только при `mRequiresSupplementalResource = True` —
  `{ itemId, perMJ }`, где `itemId` — общий `mSupplementalResourceClass` всех
  топлив, `perMJ = mSupplementalToPowerRatio / 1000` м³ на МДж.
- `provenance`: `catalogVersion`, источники и sha256, `importedAt`, текст
  проверки.
- Импорт останавливается с ошибкой, если: класс не найден или NativeClass иной;
  `mPowerProduction ≤ 0`; топливо или вспомогательный ресурс не сопоставлены
  с предметом каталога; признак жидкости каталога не совпадает с `mForm`
  (`RF_SOLID` — твёрдое); `energy ≤ 0`; у топлив разные вспомогательные ресурсы.
- Контроль с цифрами игры: угольный — 75 МВт, 15 угля/мин и 45 м³/мин воды;
  топливный — 250 МВт и 20 м³/мин топлива.

### Расчёт

- Чистая функция `powerCoverage(catalog, average, peak)` в
  `packages/domain/powerCoverage.ts`. Если `catalog.version` не совпадает
  с `provenance.catalogVersion`, она возвращает `null`.
- Для каждой мощности `P` (средняя, пик) и генератора мощностью `G`:
  - генераторов: `ceil(P / G − 1e-9)`, при `P ≤ 0` — 0;
  - расход топлива: `P · 60 / energy` в единицах каталога в минуту. Генераторы
    сжигают топливо пропорционально выдаваемой мощности, поэтому для средней
    мощности расход считается от средней, а не от числа генераторов;
  - вспомогательный ресурс: `P · 60 · perMJ` м³/мин.
- Генераторы считаются на 100% без усилителей и без Somersloops.

### Интерфейс

- В разделе «Энергия» результата (`Results.tsx`, `energy-panel`) — раскрывающийся
  блок «Чем покрыть» в общем стиле `details`. Показывается, если `powerCoverage`
  не `null` и средняя мощность больше 0.
- Источник мощностей — та же `ConstructionModel`, что и строки раздела:
  средняя — `model.averagePower`, пик — `model.peakPower + powerReserve`.
  При резерве больше 0 столбец называется «Пик + резерв», иначе «Пик».
- Для каждого генератора: строка с числом генераторов для средней и пиковой
  мощности; затем строки топлив с расходом при средней и пиковой мощности;
  у угольного — строка воды.
- Оговорка: «Справка: генерация не входит в оптимизацию. Генераторы на 100%
  без усилителей; добычу топлива и воды план не включает.»

## 4.2 Карточки вариантов по мере готовности

### Решатель

- `solveVariants(catalog, input, highs, deadline, onProgress?)`: порядок
  вариантов и доли срока (0,25 / 0,5 / 0,75 / 1,0) не меняются. После решения
  каждого варианта сразу вычисляется его `sameAs` (сравнение только с предыдущими
  вариантами, как сейчас), затем вызывается
  `onProgress(report, pending)`, где `pending` — id ещё не решённых вариантов.
  Пока `pending` не пуст, `report.equivalent = false`: совпадение всех режимов
  нельзя утверждать до решения последнего (уточнено при реализации 2026-10-22).
- Возвращаемый отчёт совпадает с прежним итоговым. Тип `ProductionVariants`
  не меняется. При ошибке `parsePlan` `onProgress` не вызывается.

### Worker и протокол

- `solver.worker.ts` отправляет сообщения
  `{ report: ProductionVariants; pending: ProductionVariant['id'][]; done: boolean }`.
  Промежуточные — `done: false`; последнее — `done: true` и пустой `pending`.
  Ошибка загрузки решателя — одно сообщение `done: true` с прежним вариантом
  «Расчёт недоступен».

### `useSolver`

- Каждое сообщение обновляет отчёт. `running` остаётся true до `done: true`.
  Новый возвращаемый `pending` — id нерешённых вариантов текущего отчёта.
- `choose` принимает решённый вариант и во время расчёта. Выбор не
  останавливает worker: план после выбора равен принятому снимку того же
  запроса. Правило остановки: worker останавливается, когда текущий план не
  равен ни входу запроса, ни принятому снимку этого запроса.
- Отмена, общий таймер 30 с, `onerror` и правка плана останавливают расчёт
  как сейчас. Частичный отчёт сохраняется; нерешённые варианты получают
  отметку «не рассчитан», причина — текст ошибки хука.
- Ответ устаревшего worker по-прежнему не принимается.

### Карточки

- Нерешённый вариант при идущем расчёте: плашка «Считается…», без метрик
  и кнопки выбора.
- Нерешённый после остановки: плашка «Не рассчитан» и причина.
- Решённый вариант выбирается сразу; совпавший сворачивается в подпись `sameAs`,
  когда решается.
- Заголовок экрана во время расчёта — «Варианты производства». После выбора
  во время расчёта — подробный план выбранного варианта; «Вернуться к вариантам»
  показывает текущее состояние карточек.

## Вне объёма

Биомасса, АЭС, геотермальные генераторы; разгон генераторов; генерация как часть
оптимизации; учёт открытия генераторов в мире; параллельное решение вариантов
в нескольких worker.

## Проверки

- Vitest:
  - `powerCoverage`: 300 МВт → 4 угольных, 60 угля/мин, 180 м³ воды; ровно
    75 МВт → 1; 0 МВт → 0; несовпадающая версия → `null`; топливо 250 МВт →
    1 генератор, 20 м³/мин;
  - данные `power-generators.json`: мощности и энергоёмкость против цифр игры,
    версия каталога;

    и три id в `pending`; последний отчёт совпадает с возвращаемым.
- Playwright:
  - блок «Чем покрыть» в результате выбранного варианта;
  - карточка максимума доступна до конца расчёта; после выбора и возврата к
    вариантам карточки заполнены.
