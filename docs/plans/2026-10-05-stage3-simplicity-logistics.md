# Этап 3: простота и логистика

Запрос пользователя 2026-10-05: «начинай» — следующий этап плана
[среднего этапа](2026-10-03-mid-game-roadmap.md). Дизайн согласован в диалоге
2026-10-05: отдельная настройка бюджета машин для простоты (по умолчанию 10%),
допустимая потеря выпуска как у остальных экономичных вариантов. Ниже —
принятые решения.

## 3.1 KPI простоты

- Чистая функция `buildComplexity(plan, result)` в `packages/domain/complexity.ts`;
  решатель и контракт `Result` не меняются.
- «Разных рецептов» — число уникальных `recipeId` среди `result.steps` с
  `cycles > 0`. Добыча (`result.resources`) и утилизация в число не входят.
- «Промежуточных предметов» — предметы, у которых есть положительный выход
  хотя бы одного этапа и положительный вход хотя бы одного этапа. Целевые
  продукты плана исключаются; жидкости учитываются. Сырьё из источников,
  которое ни один этап не выпускает, промежуточным не считается.
- Результат: `kpi-grid` получает две новые плитки «Разных рецептов» и
  «Промежуточных предметов»; значения берутся из `buildComplexity`.
- Карточки вариантов: строка «Разных рецептов» с разницей к максимальному
  варианту, как у мощности.
- Решатель в финальном тай-брейке считает только рецепты с положительной
  энергией цикла; KPI считает все этапы результата. Расхождение возможно лишь
  для рецептов без потребления энергии и не выдаётся за значение цели решателя.

## 3.2 Вариант «Проще построить»

- `ProductionVariant.id` расширяется значением `simple`, подпись
  «Проще построить». Порядок карточек: максимальный, экономия энергии,
  экономия редкого сырья, проще построить; максимальный остаётся первым.
- Настройки:
  - `settings.variantOptions.simplerExtraPercent?: number` — допустимое
    добавление машин в процентах от минимума, 0–1000, по умолчанию 10.
    Отсутствующее поле означает 10; старые планы не мигрируют.
  - `settings.recipesFirst?: { extraPercent: number }` — флаг решателя,
    выставляется только копией плана варианта. Поле взаимоисключающее с
    `resourcesFirst` и `smoothPowerExtraMachines`; zod отклоняет сочетание.
- Потеря выпуска: `outputSlack = variantOptions.outputLoss ?? 10` для
  максимизации без партии, иначе 0 — как у остальных экономичных вариантов.
  Жёсткие `minRate/maxRate` и политики выпуска сохраняются.
- Порядок целей в `solve` при `recipesFirst`:
  1. Цели выпуска (с допустимой потерей, как сейчас).
  2. Минимум целых физических машин `machineCount`, округление.
  3. Бюджет `B = minimum + ceil(minimum · extraPercent / 100)`; ограничение
     `machineCount <= B`. При `extraPercent > 0` и `minimum > 0` добавляется
     хотя бы одна машина. `Result.machineBudget = { minimum, limit: B, used }`,
     `used` пересчитывается validator как у экономии энергии.
  4. Минимум числа разных рецептов: одна бинарная переменная на `recipe.id`,
     общая для всех конфигураций рецепта; для каждого рецепта
     `Σ countVariable(конфигурации) − B · used ≤ 0`. Граница доказана бюджетом
     машин, произвольный big-M не используется. Рецепты всех конфигураций с
     `countVariable` учитываются независимо от энергии цикла. Существующие
     линии фиксируют свой счётчик, поэтому их рецепт считается использованным.
  5. Затем `machineCount` → средняя мощность → взвешенное сырьё; каждая цель
     фиксируется с прежним допуском.
- Выбранные бинарные значения фиксируются; неиспользованные рецепты получают
  верхнюю границу потока 0 (как в существующем тай-брейке). Финальный блок
  «минимум рецептов при зафиксированной мощности» для `recipesFirst`
  пропускается: число рецептов уже зафиксировано. Целые количества и
  перепроверка допустимости — общим механизмом `integerFlows`.
- Если `countVariable` отсутствует (цель без целых машин), `recipesFirst`
  не применяется: варианты всегда решаются в smooth-power, где счётчики есть.
- `modelNotes`: «Минимум разных рецептов найден в пределах бюджета машин
  (минимум + N%). Вне бюджета более простой план не исключён.»
- Принятый вариант передаёт `recipesFirst` в текущий план (как сейчас
  `resourcesFirst`). Поэтому `costOrder` в `analysis.ts` получает ветку
  `recipesFirst`: число разных рецептов → машины → мощность → сырьё;
  сравнения и рейтинг альтернатив упорядочивают пользу в этом порядке.
- Время: прежний общий срок 25 с; доли срока 0,25 / 0,5 / 0,75 / 1,0 по
  порядку карточек, неиспользованное время переходит дальше. Ошибка или
  тайм-аут одного варианта не стирает остальные.
- `sameAs`: сравнение с предыдущими вариантами без `sameAs` прежнее;
  `equivalent` истинно, если все остальные варианты совпали с максимальным.
- Интерфейс:
  - подсказка карточки: «Сначала минимум разных рецептов в пределах
    компактной фабрики + N%, затем машины и энергия.» и прежний текст про
    потерю выпуска;
  - `VariantSettings`: поле «Дополнительные машины для простоты, %»;
    текст «Оба варианта» заменяется описанием всех вариантов.

## 3.3 Граница фабрики

- Общая функция `parallelLines(rate, capacity)` в `packages/domain`:
  `rate > 0 ? max(1, ceil(rate/capacity − min(1e-7, rate/capacity·1e-8))) : 0`.
  `Results.tsx` и `schematic.ts` используют её вместо собственных копий.
- Входы: строка источника в «Загрузке источников» показывает
  «N лент/труб» выбранного уровня (`model.transport`, уже ограниченного миром)
  для фактического расхода.
- Выходы: готовая продукция — как сейчас; отгрузки переносятся из текстовой
  строки в панель «Отгрузки» со значением потока и числом линий.
- Утилизация в Sink — машина внутри фабрики, не выход границы; её потоки
  в счёт границы не входят.
- Подсказка: для месторождения число линий относится к суммарному потоку через
  границу; предел выхода каждого добытчика проверяется отдельно моделью.

## Проверки

- Vitest:
  - `buildComplexity`: ручной пример, цикл, побочный продукт, целевой продукт,
    частично потребляемый внутри;
  - контрольный план, где `simple` при 10% использует меньше разных рецептов,
    чем `maximum`, и при `extraPercent = 0` не превышает бюджет минимума;
  - бюджет машин `simple` пересчитывается validator; материальный баланс;
  - отклонение сочетания `recipesFirst` с `resourcesFirst`/бюджетом экономии;
  - тайм-аут одного варианта не стирает остальные (4 карточки);
  - `parallelLines`: граница целого, ноль, жидкость.
- Playwright: четвёртая карточка и её выбор; KPI результата; число линий у
  источников и отгрузок; клавиатурный доступ к новому полю настроек.
- `pnpm typecheck`, `pnpm build`; полный `pnpm test` и `pnpm test:ui`.
